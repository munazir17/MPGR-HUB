# Genuine Base limit orders: feasibility and approval proposal

Research date: 2026-10-17. **Research only. No protocol was integrated, no order was signed, no credentials were changed, and no transaction was submitted.** Sources below were read through the official repositories using GitHub's API, not through a live trading API. Published deployments are not proof of deployed bytecode, service health, asset eligibility or fill availability.

## Decision

**Do not enable executable limit orders in this PR.** The current constraints require unchanged MPGR contracts, Executor behavior, signing/Permit2 semantics, fee logic and execution routing. None of the candidates below is a demonstrated drop-in for those constraints. A price alert, local draft, reference-price trigger or separately authorized Agent goal is not a protocol limit order.

For a separately approved feasibility phase, prioritize **CoW's Base orderbook integration** because its published SDK explicitly identifies a Base orderbook, signed orders/cancellations and order/trade status reads. This is a candidate for evaluation, **not a compatibility or availability claim, not approval to add it, and not a recommendation to replace current spot routing**. Keep 1inch v4 as a second candidate if its Base orderbook eligibility and fee requirements can be established. Do not equate the existing 0x Swap API integration with a working Base limit-order service.

Under the present unchanged-routing constraint, the product must remain explicitly unavailable. A future approval would need to state whether an external settlement protocol is acceptable while leaving deployed MPGR contracts unchanged. If it is not acceptable, this research does not establish a compliant implementation.

## Approval and engineering gates for any later proposal

1. **Explicit protocol/settlement approval:** resolve the unchanged-routing incompatibility first. No alternate executor, new signature domain, protocol SDK or order-submission endpoint is added by this PR.
2. **Pinned code and deployment verification:** identify audited release/commit, Base 8453 contract bytecode, feature registrations, spender and verifying contract. Read the relevant audit reports; this source review is not an audit.
3. **Service/asset eligibility:** verify Base API availability, commercial/API-key requirements, orderbook/filler coverage and supported assets. B20 eligibility must be confirmed specifically; existing Aerodrome spot liquidity does not imply a protocol will list or fill B20 orders. Do not promise arbitrary imported-token fills.
4. **Fee-equivalence proof:** preserve 25bps sell-token basis, rounding and gross/net accounting on both directions and partial fills. Itemize protocol/partner/network fees, include them in signed order limits, prove same-settlement collection, and rule out duplicate charges. No separate fee-transfer transaction or silently substituted fee token/basis.
5. **Wallet consent/security review:** exact order fields, price/minimum, sell cap, receiver, chain/domain, partial-fill preference and expiry must be visible. Approvals and signatures must be explicit and independently validated. No broad Agent-chat permission, signing by a model, server-held user key or reuse of another goal's authorization.
6. **Order lifecycle and authoritative status:** signed ≠ submitted ≠ accepted ≠ partially filled ≠ filled. Track protocol UID/hash, remaining amount, expiry, cancellation requested/accepted/on-chain invalidation, settlement transactions and decoded fills. Reconcile service outages/restarts and fill/cancel races. Never display price-trigger success as settlement.
7. **Offline then separately authorized acceptance:** deterministic API/contract mocks, domain/receiver/fee tampering, cancellation races, partial-fill accounting, unsupported assets and unavailable-service cases first. Authenticated read-only provider checks and any live signing/filling require separate user authorization. This task forbids live orders/trades.

### Deliberately unverified

Live API health, account entitlements, commercial terms, hosted orderbook support for 1inch/0x on Base, native feature registration/bytecode, B20 eligibility, actual fills, exact gas/cancellation costs, fee-equivalent integration, and compatibility with the unchanged MPGR Executor remain unverified. External service hosts are outside this workspace's outbound allowlist. No attempt was made to bypass that restriction, obtain signing credentials or submit test orders to production.
