## Actual main-thread findings and changes

1. **Measured synchronous asset work.** The loader previously called `stripBackgroundToTransparent` immediately after decode for three large images. Three native/V8 trials per asset measured:
   - Legacy side run-2: **102–122 ms**.
   - Chest: **73–84 ms**.
   - Checkpoint: **126–153 ms**.
   These are full-image readback + flood-fill + writeback timings, with decoding outside the timed section. Such work can delay a queued interaction or its next paint. It does **not** establish that it caused the user's specific recording.
   - Those exact border-fill results are now **lossless offline WebP cutouts**, on fresh URLs. No live preload path needs background removal; `BACKGROUND_STRIP_TARGETS` is empty. The old helper/loader capability remains for compatibility, not on the current loading path.
   - All alpha bytes and visible RGB match the previous native runtime output. RGB beneath alpha=0 may be discarded by WebP. Originals remain on disk. See [prebake audit](prebake-audit.json).
2. **Unnecessary React work.** The 120 ms HUD timer previously updated the whole game component, controls and phase overlays. Only the new HUD leaf now subscribes to a stable external store; unchanged snapshots/power-up display seconds do not notify it. Canvas, controls and phase overlays no longer reconcile on HUD ticks. The timer cadence and displayed score calculation remain unchanged. World, trace and sprite-container refs initialize lazily instead of allocating discarded initial values on every React render. This is a structural reduction, not a measured React-Profiler/device-INP result.
3. **Redundant canvas resets.** ResizeObserver, viewport events, settle timers and phase transitions previously reassigned backing dimensions even at identical sizes. Identical size/DPR now returns early; CSS-size/DPR changes still update the transform and viewport. The DPR cap is unchanged.
4. **Per-entity frame garbage.** The painter queue reuses entries after warm-up; it no longer creates a drawing closure/object for each visible entity each frame. Equal-depth ordering is preserved. **66/66 native fixture PNGs were byte-identical across the queue-only change** before subsequent art polish; [hash evidence](queue-parity.json). This is not a claim of a completely allocation-free Canvas renderer: native gradients, a few per-frame helper closures and fallback paths still exist.
5. **Live overlay filtering.** In-run HUD/controls use readable translucent fills instead of backdrop blur over a changing canvas. Existing diagnostic warnings remain untouched. The compositor benefit is not quantified without a browser/device trace.

The pointer handlers already perform bounded ref/trace updates; no per-frame React state was found in the simulation/render loop. The new local report below is intended to distinguish delayed event dispatch from handler work and delayed presentation rather than treating every latency issue as blur.

## Capturing the outstanding device latency

1. On the affected device, load `/games/mpgr-run?runPerf=1` through the normal authenticated app. This is an opt-in diagnostic flag, **not** an auth bypass or a new game route.
2. Use normal inputs and reproduce the slow interaction. Keep a browser Performance recording covering it, ideally both a cold start and an already-loaded run. Note device/browser, whether this is a development or production build, and orientation.
3. Through remote browser DevTools, inspect `window.__mpgrRunPerformance.snapshot()` or call `window.__mpgrRunPerformance.download()` to save the local JSON.
4. Compare event input delay, handler time and presentation delay with long tasks and renderer/simulation JS samples. Presentation delay can include raster/compositing that JS draw-command timing cannot measure. Pair the report with the actual Performance trace and the requested action/world recording.

No network telemetry, wallet identifiers, DOM text, coordinates or gameplay state are collected. Observers are opt-in and disconnected on unmount. Per-frame samples use fixed typed buffers; event/long-task lists are bounded. Unsupported APIs are explicitly reported, not treated as zero latency. This is a **triage report, not an INP implementation**: durations are browser-quantized, sub-16 ms entries omitted, only recent samples retained, and no page-wide percentile is claimed.
